# 抖音助手跨电脑实施方案

> **设计草案，尚未接通真实跨电脑任务。** 当前能登记多个账号、设备和本机资料权限；远端登记不代表另一电脑已经在线处理，也不能把本机同号知识库授给远端。

本草案说明已有隔离基础、缺口与后续验收顺序，不是部署指南、已上线能力或多人生产服务承诺。日常使用见[助手使用说明](抖音助手使用说明.md)。

## 目标与职责

| 角色 | 建议负责的事情 | 不能直接获得的能力 |
| --- | --- | --- |
| B所在接待主机（Hub，任务接待端） | 独占受控B会话；核对真实评论、原线程及公开许可；保存任务与发送屏障 | 不因转交任务就读取用户整库、任意文件或任意地址 |
| 资料电脑 | 只操作本机明确允许的知识库，使用原下载、识别、检索与问答流水线 | 不替其它电脑发布，也不接受模型提供的任意目标 |
| 本机操作者 | 配对设备、选择范围、撤销权限、处理本人核验 | 本机声明不能替代平台认证或真实消息来源证明 |

资料电脑宜主动连接预先登记的固定接待端，领取自己的任务并上报状态；服务地址和身份须由配对配置决定，不接受评论或模型随意指定网络地址。**当前没有实现这条真实连接。**

未允许公开的结果应留在资料电脑；云端模型仍可能收到被选出的资料片段。本机保存不等于完全离线，联网设计也不能自动增加公开权限。

## 已有基础与未完成部分

| 现有模块 | 可复用基础 | 仍缺少的真实能力 |
| --- | --- | --- |
| Registry（用户、设备、库授权台账） | 本机权限、撤销版本、明确资料范围 | 可撤销的远端配对、远端目录与设备身份实证 |
| 签名消息 | 固定目标、正文校验、HMAC（共享密钥消息校验）、有效期及nonce（一次性消息编号） | 真实平台来源与业务持久接收不能只靠签名证明 |
| AssistantQueue（本机任务队列） | 原评论去重、冻结范围、执行/发表领取与未知屏障 | 双端任务号、接收回执和结果的持久对应 |
| DeviceInbox（隔离接收基础） | 接收、查询回执、限定交接与冲突检查 | 未接入日常远端生产路由，不证明任务已经执行 |
| 入库回执 | 原后台负责，按目标库、视频与正文索引核对状态 | 每台资料电脑的真实后台归属及可信只读状态转交 |
| 发表台账 | 一次发送预约、未知不自动重发 | 远端结果与真实原线程、双端公开授权的联合核对 |
| SQLite协作锁与归属保护 | 同机短事务互斥、确认归属后的正常数据库恢复 | 不提供跨电脑网络，也不使两个数据库的交接自动成为原子事务 |

## DeviceInbox目前的严格边界

隔离模块提供 `accept`（持久接收）、`get_receipt`（按回执核对）、`get_receipt_by_remote_task`（按对方任务号核对）和限定handoff（交接）方法。接收到消息、交接到本地任务、模型执行、入库成功与公开回评是不同阶段。

它目前只接受 `source_mode=isolated/replay`（隔离或回放来源）。设备自称 `live_ui`（真实页面来源）会被拒绝；公开回执的 `platform_origin_verified=false`（未证实平台来源）和 `execution_enabled=false`（未启用执行）不能通过客户端布尔值改成真实授权。模块未提供通用远端用户HTTP接口。

因此，不应将该模块的单元测试或临时两个目录模拟称为“多人跨电脑已能用”。

## 设计必须处理的边界

### 接收确认丢失与崩溃

nonce已经记录而任务尚未入队时退出，重新提交可能只得到“消息已用”。后续协议需要持久接收记录、稳定对方任务号和只读对账；不能把重复拒绝当成“任务一定成功”，也不能为恢复而删除nonce。

不同数据库间需明确意图、交接和确认阶段。崩溃后先核对原记录，不重新支付模型或重复提交导入、评论。

### 身份与资料范围

数字相同的知识库ID只在其所属设备中有意义。远端需要真实目录版本、撤销能力与配对身份，不能借用本机同号库。

复制Registry、浏览器资料或UUID（逻辑实例编号）不等于得到独立的物理设备身份；旧数据库副本不能成为另一台电脑的授权凭证。

### 当前权限与任务历史

签包时有效不代表执行时仍有效。领取、工具、结果接收与发表应重新核对当前范围；授权变化后拒绝不能靠换包、换nonce或覆盖旧冻结目标来绕过。

未允许公开的答案与正文不应为“状态同步”而上传给接待端。先定义最小结果字段，再接真实网络。

### 平台原评论与一次发送

持有消息密钥不证明谁真正 @ 了B。真实评论、视频、A/B身份和原线程仍需独立核对；模型和远端设备不能提供一个“已核对”布尔值来代替证据。

发送前仍由B所属主机重新定位与核验。结果未知时保留发送屏障，不因两端超时、确认丢失或重新上线而再发一次。

## 后续建议验收顺序

1. **协议与隔离数据**：锁定设备身份、库命名空间、回执、撤销和最小结果；验证崩溃/并发/重复消息。
2. **真实设备只读连接**：两台实际电脑完成配对与只读状态核对，不调用模型、不导入、不发表。
3. **单一授权任务**：在明确授权下完成一次真实领取、处理与对账，费用和失败能追踪。
4. **原线程闭环**：另行验证真实收件、对应资料电脑处理、B一次发表、B回读及A独立可见。
5. **稳定性与撤销**：断线、重启、过期、撤销与本人核验分别验收；不能只用一段空闲观察代替。

在上述步骤完成前，界面出现 `waiting_desktop`（等待电脑）或远端登记，只能说明等待/未接通，不应显示远端已在处理，更不能回退到本机资料答题。

## 历史 / 开发参考

早期已在临时合成数据中检查过消息重复、回执丢失、归属和跨库隔离，并保留过失败与修复版本。原始工程全文及涉及本机真实运行的证据由维护者私有保存；本公开稿不包含真实账号、视频、设备凭据、任务号或私人报告链接。

隔离检查不是实际跨电脑部署，旧的单电脑问答成功与回评可见也不是跨电脑验收。本文没有开放公网端口、创建远端凭据或增加产品权限。
